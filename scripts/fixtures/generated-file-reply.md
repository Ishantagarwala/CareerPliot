Read the examples, trace the output, then try the practice questions at the end.\n\n## Part 1: Closures\n\n### What is a closure?\n\nA **closure** is a function that remembers the variables from the scope where it was created, even after that scope has finished executing. In JavaScript, every function closes over its lexical scope — the scope that was in effect where the function was defined, not where it was called.\n\n### How it works\n\nWhen you define a function inside another function, the inner function keeps a reference to the outer function's variables. Those variables stay alive in memory as long as the inner function exists.\n\n```js\nfunction makeCounter() {\n  let count = 0; // this variable is \"closed over\"\n\n  return function () {\n    count += 1;\n    return count;\n  };\n}\n\nconst counter = makeCounter();\n\nconsole.log(counter()); // 1\nconsole.log(counter()); // 2\nconsole.log(counter()); // 3\n```\n\n`makeCounter` has already returned, but the inner function still has access to `count`. Each call to `makeCounter()` creates a fresh closure with its own independent `count`.\n\n### Practical uses\n\n**1. Private state / encapsulation**\n\n```js\nfunction createUser(name) {\n  let password = 'hunter2';\n\n  return {\n    getName: () => name,\n    setPassword: (newPass) => { password = newPass; },\n    checkPassword: (candidate) => candidate === password\n  };\n}\n\nconst user = createUser('ada');\nconsole.log(user.getName());        // ada\nconsole.log(user.checkPassword('hunter2')); // true\nuser.setPassword('new-secret');\nconsole.log(user.checkPassword('hunter2')); // false\n```\n\n`password` is not a property of the returned object — it can only be touched through the closure. This is the same idea behind the module pattern and behind React's `useState` and `useEffect`, which capture values via closures.\n\n**2. Callbacks and event handlers**\n\n```js\nfunction setupButton(buttonId, message) {\n  const button = document.getElementById(buttonId);\n  button.addEventListener('click', () => {\n    console.log(message); // message is captured from the outer scope\n  });\n}\n```\n\n### Common pitfall: closures in loops\n\n```js\nfor (var i = 0; i < 3; i++) {\n  setTimeout(() => console.log(i), 0);\n}\n// Output: 3, 3, 3\n```\n\n`var` is function-scoped, so all three callbacks share the same `i`. By the time they run, the loop has finished and `i` is `3`.\n\nUsing `let`, which is block-scoped, creates a new binding for each iteration:\n\n```js\nfor (let j = 0; j < 3; j++) {\n  setTimeout(() => console.log(j), 0);\n}\n// Output: 0, 1, 2\n```\n\nIf you must use `var`, wrap the body in an IIFE to capture the value:\n\n```js\nfor (var k = 0; k < 3; k++) {\n  ((n) => setTimeout(() => console.log(n), 0))(k);\n}\n// Output: 0, 1, 2\n```\n\n## Part 2: The Event Loop\n\nJavaScript is single-threaded: it runs one thing at a time. The event loop is how the runtime handles asynchronous work without blocking.\n\n### The pieces\n\n- **Call stack** — where synchronous code runs, one function at a time.\n- **Web APIs / Node APIs** — browser or Node features such as `setTimeout`, `fetch`, and DOM events. They run outside the call stack.\n- **Task queue (macrotask queue)** — holds callbacks from `setTimeout`, `setInterval`, I/O, and DOM events.\n- **Microtask queue** — holds callbacks from `Promise.then`, `catch`, `finally`, `queueMicrotask`, and the continuation of `async` functions.\n- **Event loop** — checks the queues and moves work back onto the call stack when it is empty.\n\n### Order of execution\n\n1. Run all synchronous code until the call stack is empty.\n2. Drain the **entire** microtask queue.\n3. Take **one** task from the task queue and run it.\n4. Repeat: microtasks again, then one task, and so on.\n\n### Example: predicting output\n\n```js\nconsole.log('1: script start');\n\nsetTimeout(() => console.log('2: timeout'), 0);\n\nPromise.resolve().then(() => console.log('3: promise'));\n\nconsole.log('4: script end');\n\n// Output:\n// 1: script start\n// 4: script end\n// 3: promise\n// 2: timeout\n```\n\nWhy: `1` and `4` are synchronous. The promise callback is a microtask, so it runs before the `setTimeout` callback, which is a task. Even with a delay of `0`, the timeout still has to wait for the microtask queue to empty.\n\n### Diagram\n\n```mermaid\nflowchart TD\n  A[Call Stack] -->|\"setTimeout, fetch, events\"| B[Web APIs]\n  B -->|\"callback ready\"| C[Task Queue]\n  A -->|\"Promise.then, async/await\"| D[Microtask Queue]\n  D -->|\"event loop pushes, runs first\"| A\n  C -->|\"event loop pushes, one per turn\"| A\n```\n\n### Why this matters for full-stack work\n\n- Async order determines when UI updates, API responses, and database queries actually take effect.\n- Promises and `async/await` are microtasks; timers and I/O are tasks. Mixing them carelessly causes subtle race conditions.\n- In Node.js, `process.nextTick` runs before the microtask queue — one more ordering detail worth knowing.\n\n## Quick Reference\n\n| Kind of callback | Queue | When it runs |\n| --- | --- | --- |\n| `Promise.then`, `catch`, `finally`, `async/await` continuation, `queueMicrotask` | Microtask queue | After every task, before the next task |\n| `setTimeout`, `setInterval`, I/O, DOM events | Task queue | One task per event loop turn |\n\n## Practice Questions\n\n**1. All synchronous code first (`A`, `E`), then the microtask queue drains (`C`, `D`), then the task runs (`B`).\n\n**2.
